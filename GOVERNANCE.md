# Project Governance

This document outlines the governance model for the Constraint-Native Generative Engine project.

## Benevolent Dictator for Life (BDFL) Model

Constraint-Native Generative Engine is managed under a Benevolent Dictator for Life (BDFL) model.

- **BDFL / Project Lead:** The main project creator / maintainer (referred to as the "Maintainer").
- The Maintainer holds final authority on all project decisions, including roadmap directions, architecture design, pull request approvals, release cycles, and dispute resolutions.

## Consensus & Contribution Mechanics

While the Maintainer makes all final decisions, we value community input and aim for a consensus-driven approach to discussion:

1. **RFCs & Issue Discussions:** Major design changes, API redesigns, or feature proposals should start as issues or RFC discussions where the community is invited to comment and refine proposals.
2. **Pull Request Review:** All code contributions are submitted as Pull Requests. Community members are encouraged to review, comment on, and test PRs.
3. **Final Decisions:** If a consensus cannot be reached naturally during discussions, the Maintainer will make the final decision. The Maintainer reserves the right to reject, modify, or accept any pull request.

## Scope of Governance

The governance of the project spans the following areas:

- **Pull Requests & Code Reviews:** Reviewing and merging external contributions.
- **Roadmap & Architecture:** Setting the project's direction, deciding on features, design patterns, and module boundaries.
- **Release Management:** Managing tags, versions, and release distributions.
- **Community Standards:** Enforcing the Code of Conduct and managing project spaces (e.g. issues, discussion boards).
