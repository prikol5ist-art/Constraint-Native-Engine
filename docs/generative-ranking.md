# Generative Ranking and Validation

The engine supports integrating remote artificial intelligence or large language models (LLMs) to perform subjective rank evaluation on top deterministic solutions. This document explains the generative ranking interface, request and response serialization, validation checks, and reordering fallback mechanics.

---

## 1. The `GenerativeRanker` Interface

The `GenerativeRanker` interface isolates remote ranking execution from the core solver. It is a suspending functional interface:

```kotlin
fun interface GenerativeRanker {
    suspend fun rank(request: RankingRequest): RankingResponse
}
```

*   **Suspending**: Runs asynchronously inside Kotlin Coroutines, supporting cooperative cancellation and non-blocking IO.
*   **Decoupled**: Does not make assumptions about transports, credentials, or target LLM vendors.

---

## 2. Request and Response Payloads

To communicate with an LLM, the orchestrator collects solutions and user context into standard transport payloads.

### Request Payload (`RankingRequest`)
*   `solutions: List<RankableSolution>`: A list of candidate solutions to rank.
    *   `id: SolutionId`: The canonical ID of the solution.
    *   `summary: String`: A human-readable text representation of the solution generated by a `ContextRenderer`.
*   `contextSummary: String`: Contextual instructions (e.g. occasion, user profile attributes, weather).

### Response Payload (`RankingResponse`)
*   `rankedSolutions: List<RankedSolution>`: The model's suggested solution sequence.
    *   `id: SolutionId`: The canonical ID matching the input solutions.
    *   `explanation: String?`: Optional text justification for the ranking.

### Safe Serialization (Escaped JSON)
When utilizing the Gemini API via `:adapter-gemini`, the request is sent with a strict JSON Schema configuration (`responseSchema`), instructing the LLM to output a JSON object adhering to the structure:
```json
{
  "type": "OBJECT",
  "properties": {
    "ranked": {
      "type": "ARRAY",
      "items": {
        "type": "OBJECT",
        "properties": {
          "solution_id": { "type": "STRING" },
          "explanation": { "type": "STRING" }
        },
        "required": ["solution_id"]
      }
    }
  },
  "required": ["ranked"]
}
```
All variables, candidate attributes, and user instructions are serialized and escaped inside the JSON request body. This prevents the LLM from executing prompt injection commands since instructions and data are strongly separated.

---

## 3. Strict Safety Validation via `RankingValidator`

Every response returned by a `GenerativeRanker` must undergo validation via `RankingValidator.validate(response, knownSolutions)`. If any check fails, the ranker status is marked as `FELL_BACK` and the error is logged.

The validator enforces the following rules:

1.  **Non-Empty Validation**: The LLM response must contain at least one ranked solution candidate.
2.  **No Hallucinated/Unknown IDs**: Every returned `solution_id` must match a canonical `SolutionId` from the input solutions generated by the deterministic solver. Any unknown ID triggers rejection.
3.  **No Duplicates**: A single `solution_id` cannot appear multiple times in the ranked response.
4.  **No Excessive Candidates**: The ranker cannot return more solutions than the number of candidates originally provided for ranking.
5.  **Explanation Character Limits**: If an `explanation` is provided, it must not exceed 2,000 characters.
6.  **No Control Characters**: Explanation texts are rejected if they contain ISO control characters (excluding standard whitespace formatting characters `\n`, `\r`, `\t`) to defend against control character hijacking.

---

## 4. Deterministic Local Fallback and Reordering

When validation passes, the system reorders the deterministic solutions based on the ranker's preferences. However, if some solutions were omitted by the ranker, or if the ranker fails entirely, the system invokes deterministic recovery rules.

### Subset Reordering (Omitted Solutions)
If the ranker returns a valid subset of the input solutions, the engine preserves the ranker's order for those items, and then appends the omitted solution candidates in their original deterministic score order.

**Reordering Algorithm (`ValidationResult.Valid.reorder`)**:
```kotlin
fun <A> reorder(original: List<FeasibleSolution<A>>): List<FeasibleSolution<A>> {
    val originalMap = original.associateBy { it.id }
    val reordered = mutableListOf<FeasibleSolution<A>>()
    val addedIds = mutableSetOf<SolutionId>()

    // 1. Insert ranked solutions in ranker's suggested order
    for (ranked in rankedSolutions) {
        val orig = originalMap[ranked.id]
        if (orig != null && ranked.id !in addedIds) {
            reordered.add(orig)
            addedIds.add(ranked.id)
        }
    }

    // 2. Append any omitted solutions in original deterministic score order
    for (orig in original) {
        if (orig.id !in addedIds) {
            reordered.add(orig)
            addedIds.add(orig.id)
        }
    }

    return reordered
}
```

### Complete Fallback on Failure
If the `GenerativeRanker` execution:
*   Throws a transport or network exception,
*   Times out (exceeds `rankerTimeoutMillis`, default 5000ms),
*   Fails the validation criteria checked by `RankingValidator`,

the engine discards the ranker's response, marks `rankerStatus = RankerStatus.FELL_BACK`, and returns the local solutions in their original deterministic solver order. This ensures that network partition, rate limits, or LLM hallucination never degrades service availability.
