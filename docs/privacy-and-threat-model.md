# Privacy and Threat Model

This document outlines the security architecture, threat mitigations, and privacy design of the Constraint-Native Generative Engine.

---

## 1. Privacy Boundaries

### Telemetry-Free Core
*   **Design**: The core engine (`:engine-core`, `:engine-solver`, `:engine-generative`) contains absolutely no tracking, analytic reporting, telemetry collection, or remote phone-home code.
*   **Data Isolation**: All computations are performed locally within the executing JVM process. No data leaves the local memory space unless a custom `GenerativeRanker` is explicitly configured.

### Diagnostics and Logging
*   **Redacted Trace Events**: If tracing is enabled, diagnostic logs represent structural metrics:
    *   Sequence indexes, duration metrics, and expanded node counts.
    *   Structural constraint rejection codes (e.g. `weather_mismatch`, `laundry_exclusion`).
*   **Attributes Exclusion**: Raw database keys, profile notes, location details, visual tokens, and personal identifying information (PII) are excluded from internal logs.

---

## 2. Generative Reranking Threat Model

Integrating remote LLM models exposes systems to data leakage, prompt injection, and model hallucination. The engine implements layered mitigations at the integration boundary:

```
[Untrusted Client Context] ──► [Escaped JSON Serialization] ──► [Remote LLM Endpoint]
                                                                     │
[Validated Output Solutions] ◄── [Strict Validation Firewall] ◄──────┘
```

### Mitigations

| Threat | Risk / Impact | Mitigation |
| :--- | :--- | :--- |
| **Prompt Injection** | LLM executes arbitrary instructions embedded in user data. | **Strict Payload Separation**: User context is isolated in escaped JSON string variables (`contextSummary` and solution attributes), separated from system instructions. System prompts are static and hardcoded. |
| **Hallucinatory Solution Generation** | LLM proposes non-existent or invalid solution candidates. | **ID Verification Checks**: The `RankingValidator` rejects any returned ID that does not belong to the initial candidate set generated by the local solver. |
| **Response Manipulation / Spoofing** | LLM returns duplicate entries to bias results. | **Duplicate ID Rejection**: Any duplicate ID detected in the response causes the validator to fail and fallback locally. |
| **Control Character Hijacking** | Malicious text formatting disrupts downstream parsers. | **ISO Control Filtering**: Explanation texts containing unauthorized control characters (other than `\n`, `\r`, `\t`) are strictly rejected. |
| **Denial of Service (DoS)** | Remote service delay blocks backend threads. | **Timeout Guards**: Generative requests are governed by a configurable timeout (`rankerTimeoutMillis`, default 5000ms). Failure to reply triggers deterministic local fallback. |
| **Memory/Storage Exhaustion** | Explanations returned by LLM consume excessive memory. | **Oversized Text Validation**: Explanations exceeding 2,000 characters are rejected at the validator boundary. |

## 3. Cryptographic and Key Isolation

*   **No Key Storage**: The core libraries and Gemini adapter do not store, log, cache, or load API credentials.
*   **Injectable Transports**: The `:adapter-gemini` module delegates network operations to a `GeminiTransport` interface. The calling application is responsible for injecting the transport instance.
*   **Security Boundary**: API keys or OAuth tokens are added to HTTP headers in the application layer. The core library never accesses raw credential strings.

---

## 4. Local Resource Exhaustion

Combinatorial solvers are vulnerable to exponential state-space explosions (denial of service through CPU or memory exhaustion).

*   **Execution Budgets**: Every solve request requires a `SearchBudget` defining a maximum node expansion limit (`maxExpandedNodes`) and duration limit (`maxDurationMillis`).
*   **Active Boundary Checking**: The search loop validates limits before expanding any tree node. If a threshold is crossed, the solver halts and returns partial results, protecting host JVM thread availability.
*   **Algorithm Boundary**: Level-by-level `BOUNDED_BEAM` search limits memory overhead to a maximum state collection size of $O(\text{beamWidth} \times \text{slots})$.

---

## 5. Dependency and Build Integrity

To defend against supply-chain attacks:
*   **Strict Dependency Verification**: Gradle builds validate checksum signatures for all external plugin binaries and library archives using dependency verification files.
*   **Zero Framework Footprint**: The lack of frameworks (e.g. Spring, Jackson, etc.) keeps the attack surface area minimal.
